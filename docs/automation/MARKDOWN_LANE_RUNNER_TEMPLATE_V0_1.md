## 2. FIXED STEP SEQUENCE

Five steps before the gate. Two more steps after operator approval. No reorder. No skip. No add.

### Step 1 — READ INPUT

```text
Action:    Open input_file_path and read its content.
Allowed:   .md, .txt
Forbidden: binary files, .png/.jpg/.webp, .mp4, .zip, .pdf
Output:    Captured content in memory (or a temp buffer).
Logging:   Add input_file_path to FILES_READ in the report.
Failure:   If file does not exist, is empty, or has forbidden extension:
           - mark VERIFY_STATUS = FAIL
           - mark RESULT = FAIL_INPUT_INVALID
           - HALT
```

### Step 2 — PRODUCE ONE MARKDOWN OUTPUT

```text
Action:    Write exactly ONE .md file at output_file_path.
Constraints:
  - .md only
  - text only
  - no embedded base64 images
  - no link to anything that would trigger render
  - must NOT overwrite existing file (HALT if path exists)
  - must NOT be the pointer file, a canon doc, a lock record, a registry, or a handoff
Hard rules in effect:
  - HR1 one output file per run
  - HR3 do not approve canon
  - HR4 do not touch locked / approved / archived / canon
Logging:   Add output_file_path to FILES_CREATED in the report.
Failure:   If the write throws, the path already exists, or any constraint trips:
           - mark VERIFY_STATUS = FAIL
           - mark RESULT = FAIL_OUTPUT_INVALID
           - HALT
```

### Step 3 — RUN VERIFY GATE

```text
Command:   python .mikage/tools/verify_output.py
Capture:   stdout, stderr, exit code
PASS rule: stdout contains literal "PASS" on its own line AND exit code = 0
FAIL rule: anything else, including:
           - stdout starts with "FAIL:"
           - exit code != 0
           - stdout missing
           - subprocess timeout / exception
Logging:   In the report:
           - copy the verify_tool stdout verbatim into VERIFY_STATUS
           - if FAIL, also copy the FAIL message into ISSUES_FOUND
Failure:   - mark VERIFY_STATUS = FAIL (with the literal failure text)
           - mark RESULT = FAIL_GATE
           - HALT
Ambiguity: If the runner cannot capture or interpret the output:
           - mark VERIFY_STATUS = CHUA_XAC_NHAN
           - mark RESULT = HALT_GATE_AMBIGUOUS
           - HALT
```

### Step 4 — WRITE REPORT

```text
Action:    Write report_file_path with the fields below.
Required fields (verbatim names):
  RESULT
  FILES_READ
  FILES_CREATED
  VERIFY_STATUS
  ISSUES_FOUND
  NEXT_SAFE_TASK
Additional required fields for this lane:
  RUN_ID
  RUN_INITIATOR
  INPUT_FILE
  OUTPUT_FILE
  POINTER_FILE
  POINTER_UPDATED
  COMMIT_STATUS    = NOT_COMMITTED
  PUSH_STATUS      = NOT_PUSHED
  LANE_CHANGE      = NO
  CANON_CHANGE     = NO
  ASSET_LOCK_CHANGED = NO
Failure:   If the report cannot be written:
           - HALT
           - operator must reissue the run with a writable report path
```

### Step 5 — UPDATE POINTER

```text
If pointer_file_path == "NONE":
  - skip
  - record POINTER_UPDATED = NO in the report
  - proceed to GATE

Else:
  - Append (do not overwrite) a single new pointer entry to pointer_file_path
    containing: timestamp, run_id, output_file_path, report_file_path,
    VERIFY_STATUS, COMMIT_STATUS = NOT_COMMITTED
  - record POINTER_UPDATED = YES in the report
  - the pointer file must be operator-named in pre-fill;
    the runner refuses to silently update docs/handoff/00_LATEST_CODEX_HANDOFF.md
    unless the operator explicitly named that as the pointer
```

### GATE — HARD STOP FOR HUMAN APPROVAL

```text
The run halts here, regardless of VERIFY_STATUS.

If VERIFY_STATUS = PASS:
  - The runner waits.
  - The runner does NOT commit. The runner does NOT push.
  - The runner waits for an explicit operator directive of the form:

      OPERATOR_APPROVED = YES
      TARGET            = <output_file_path>
      REASON            = <one-line reason>
      RUN_ID            = <run_id>

  - Without this directive (exact form, exact RUN_ID), no commit / no push is permitted.

If VERIFY_STATUS = FAIL or CHUA_XAC_NHAN:
  - The runner waits.
  - Operator-only paths from here are:
      (a) FIX_AND_RERUN — operator addresses the FAIL, then issues a new run
      (b) MARK_CHUA_XAC_NHAN_AND_PARK — operator parks the run; no commit, no push
      (c) DISCARD_OUTPUT — operator deletes the failed output (per Hard Rule HR5,
          this requires explicit operator approval and is logged in a separate note)
  - In no case may the runner commit or push a FAIL / CHUA_XAC_NHAN run.

If run_initiator = SCHEDULED_UNATTENDED:
  - The runner ALWAYS halts here regardless of VERIFY_STATUS.
  - Scheduled / unattended runs may never proceed past this gate.
  - Operator review on next operator session is the only continuation path.
```

### Step 6 — COMMIT (operator-approved only)

```text
Pre-conditions (ALL required):
  - VERIFY_STATUS = PASS
  - Operator directive captured verbatim with matching RUN_ID
  - commit_allowed = YES (operator just set it)
  - run_initiator = OPERATOR (scheduled runs are blocked here unconditionally)

Action:
  - Stage exactly the files in FILES_CREATED + the report + (if updated) the pointer
  - One commit, one message, one run_id
  - Commit message format:
      <run_id>: <one-line output description>

      INPUT:   <input_file_path>
      OUTPUT:  <output_file_path>
      REPORT:  <report_file_path>
      POINTER: <pointer_file_path or NONE>
      OPERATOR_APPROVED = YES
      REASON = <operator-supplied one-line reason>

Failure:
  - If any pre-condition is missing: HALT, no commit
  - If git refuses (dirty tree, unrelated changes staged): HALT, write a follow-up note
  - If commit succeeds: record COMMIT_HASH in a follow-up commit report
```

### Step 7 — PUSH (operator-approved only)

```text
Pre-conditions (ALL required):
  - Step 6 commit succeeded
  - push_allowed = YES (operator just set it)
  - Branch matches the branch named in the pre-fill
  - No force push under any circumstance

Action:
  - Single push, single branch
  - Capture the remote response

Failure:
  - If push is rejected: HALT, write follow-up note, do not retry with --force
  - If push succeeds: record PUSH_SUCCEEDED = YES and the remote ref in the follow-up report
```
