## 2. WHY A CONTROL REFERENCE INSTEAD OF V0.3

The three V0.2 verification reports (especially `…V0_2_VERIFICATION_REPORT_ATTEMPT_006_FLUX_PRO.md` §5) isolated three failure modes that are **model-family-independent** within the flux family under prompt-only approach:

1. **POSE_HANDS_BEHIND_BACK** — both flux/dev and flux-pro default to hands-at-sides regardless of explicit positive ("Both hands clasped strictly behind the back") + explicit negative ("no hands at sides, no hands forward") prompting.
2. **SHIELD_HYBRID_PHASE_1_DORMANT** — both models drop the ~15 cm wrist-scale disc emitter from the forearm.
3. **MONOWIRE_HOLSTERED** — both models drop the slim cylindrical hilt at the hip.

These three are FAIL across all 4 real-render attempts. No text-only iteration is likely to resolve them on this model family. Mitigation requires **control conditioning** (pose / image / shape) rather than prompt text alone.

Continuing to write V0.3 / V0.4 prompt-only briefs would:
- Burn FAL credits on attempts that are statistically likely to fail again
- Produce more iterative reference noise without converging toward a canonical anchor
- Drift the Cast Lane from "produce reference assets" toward "tune prompts" — out of scope

Hence: operator halted prompt-only iteration, and this document captures the lock requirements so that whichever control approach is picked next, it has a single explicit target to satisfy.
